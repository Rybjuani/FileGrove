# Diagnóstico — 2026-11-22

Generado con `src-tauri/examples/dump_activity.rs` contra la base de producción
(`%APPDATA%\app.filegrove.desktop\app.db`), en modo solo lectura.
Este reporte no contiene rutas ni datos personales: solo códigos de error y agregados.

## 1. Errores registrados en `activity` (filas con `success = 0`)

| Código de error | Cantidad |
| --- | --- |
| `SOURCE_FILE_OUTSIDE_WATCHED_FOLDER` | 32087 |

**Interpretación:** todos los registros de actividad fallidos comparten un único
código. Cada `SOURCE_FILE_OUTSIDE_WATCHED_FOLDER` proviene de la validación
`validate_source_file` en `src-tauri/src/paths/safety.rs`: el archivo evaluado no
resultó estar dentro de la carpeta vigilada al momento de ejecutar el move
(root canónico distinto, symlink/reparse point, o drive raíz no admitido).
Con un solo código dominante, el siguiente paso es reproducir la validación
contra la geometría real de carpetas/drives (ver punto 2) — no es un error
heterogéneo de filesystem.

## 2. Volumen del disco externo

Salida de `Get-Volume -DriveLetter F`:

| DriveLetter | FileSystemType | SizeRemaining |
| --- | --- | --- |
| F | Unknown | 336588439552 bytes (~313.5 GiB) |

Espacio disponible no es el problema. El dato relevante: Windows reporta el
**FileSystemType como "Unknown"** para F:. Ese volumen no está identificado como
NTFS/exFAT por el stack de la API de volúmenes, consistente con la hipótesis de
que `canonical_path_key` / `dunce::canonicalize` resuelve el path del disco
externo de una forma que difiere del root registrado de la carpeta vigilada
(por ejemplo, drive con mount point o formato no estándar), disparando
`SOURCE_FILE_OUTSIDE_WATCHED_FOLDER` en cada intento.
